# 基于 AIHOT 迭代 AI Radar

本文面向后续修改本仓代码的开发者，说明两个项目的融合方向、能力归属和开始开发前需要明确的边界。当前代码以 AIHOT 开源框架为基础；旧 Python ai-radar 是功能、信源和评测资产的参照。2026-09-30 已补入来源配置和采集适配修复；后续生产切换、历史导入及其验证边界见[迁移清单](migration.md)，不沿用最初准备阶段的状态。

已确认的方向是：**以本仓 AIHOT 为开发基础，吸收旧 ai-radar 的优势，继续迭代 AI Radar 网站。** 本文是开发导览，不是已批准的迁移施工计划；下文的候选能力不表示已经决定采用其全部实现或参数。

2026-10-01 用户进一步收窄首期范围：先切至 AIHOT 当前产品，只迁原始内容并由 AIHOT 重算，不搬旧算法和 UI 行为；微信解读后补，评测/标注/实验资产是否迁移留作待定 issue。当前范围以[迁移清单](migration.md#2026-10-01-范围收敛与待定事项)为准，下文是后续能力地图，不是首期前置要求。

## 网页外观维护

站点提供亮色（默认）、暗色、Feedly 和 GitHub 四个选择，桌面侧栏或手机“更多”页可切换；偏好保存在当前浏览器。维护外观时先看 [GitHub 有效设计](references/github-primer.md#风格选择与继承入口) 与 [Feedly 有效设计](references/feedly-reader.md)，其中的历史发布读数只证明当次版本，不代表现在重新验收。

当前实现的共同入口是 `apps/web/app/root.tsx`：`app.css` 承载原亮色与暗色，`reader.css` 将 Feedly 覆盖限定在公开 SiteShell，`github.css` 将 GitHub 覆盖应用于公开页和后台。后台没有独立外观切换器，沿用同一浏览器已保存的选择；Feedly 覆盖不进入后台。分享海报由 API 单独生成，不随浏览器外观切换。

偏好取值、缺省亮色、首帧脚本与备份导入出口集中在 `apps/web/app/lib/local-state.ts`，选择控件是 `components/shell/ThemeSwitch.tsx`。新增页面优先复用公开 SiteShell／后台 layout 与已有语义组件；需要调整某个风格时修改其覆盖层，不把新颜色复制进各页面。组件与例外、公开／后台 scope 和验证入口分别由上述两份有效设计维护。

## 私有资料与公开阅读的开发边界

私有资料 API 不是公开读取层的另一个展示形式：`research/` 从保留文章及在线回填材料读取，公开出口仍走 `publication/`。修改资料搜索或正文读取前先读[私有资料 API](private-research-api.md)，再定位 `packages/contracts/src/research.ts`、`apps/api/src/routes/research.ts` 和 `packages/backend/src/research/`。索引准备、专用令牌、人工限制与正文完整性各有独立含义，不能用公开全文开关或正文非空代替私有权限与完整性证据；索引不就绪由请求返回错误，不在读请求中重建。

## 能力迁移地图

“适合沿用”与“候选吸收”是基于当前实现边界的建议，具体范围应在对应功能开发时确定。

| 能力 | AIHOT 已有基础 | 旧 ai-radar 可吸收的部分 | 本仓开发落点与边界 |
|---|---|---|---|
| 产品骨架 | API、worker、SSR 网站、PostgreSQL、任务队列及统一公开读取层 | AI Radar 的使用场景与展示需求 | 依托现有 `apps/`、`packages/backend/`；页面仍经 API 读取，公开出口共同消费 publication 层 |
| 行业配置 | `industry/` 集中站点、分类、主题、提示词、门槛和示范信源 | AI Radar 的品牌、关注领域和信源覆盖 | 先映射配置，无法表达的能力再进入后端扩展；不能把旧 TOML 原样视为可导入格式 |
| 采集与材料 | 六种 adapter、原文补全、来源角色、分来源调度 | X 账号池、中文与微信渠道、正文和 quoted/link 上下文积累 | 以来源身份、抓取入口、正文取得方式逐项映射；已有来源能力不等于已配置凭据或可用服务 |
| 筛选与评分 | 三态预筛、两次评分、分级门槛、分层写作 | 难例、人工标注、逐输入错误归因、材料对结果的影响分析 | 先复用证据，再决定哪些判断规则迁入；两套分数不能直接相加或替换 |
| 分类与富化 | structure 独立抽取分类、标签和事实 | 六类分类研究、推荐理由、正文与引用材料的实验经验 | 分类与写作分别确定输入和输出；研究候选不自动变成默认提示词 |
| 事件与热门 | article → fact → story、归组复核、事件综述、衰减热度 | 旧站关联条目和热门展示的使用经验 | 适合以现有事件模型为基础；旧关联链接不直接转换成“同一事件”的事实 |
| 日报与公开出口 | 日／周／月报生成，网站、RSS、公开 API、MCP 共用读取层 | 旧站按日期浏览、精选和推荐内容的需求 | 先确定读者需要的内容形态，再接已有报告和 publication 层 |
| 评测迭代 | SelectBench 与入选校准工具 | O1–O4 对象划分、原始参照、人工复核和实验记录 | 把已有案例映射到本仓具体判断点；保留原实验身份，不把旧指标直接当新架构的验收结论 |

对应源码入口在[架构地图](architecture.md)；详细对比由[对比文档](references/ai-radar-comparison.md)单独维护，这里不复制两边的全部参数。

## 数据源融合：先映射来源，再接入渠道

AIHOT 开源包给的是示范清单，不是 AIHOT 线上全量信源。旧 Radar 的配置更广，但“配置启用”也不等于当前真实采集成功。后续导入应基于对比文档的静态清单，再在目标环境验证实际抓取。

一条来源至少要核清以下关系，避免相同机构的不同入口互相冒充：

- 来源身份与实际入口：同一 RSS、同一发布方的不同栏目、官网与 X 账号分别对应什么。
- 抓取能力：已有 RSS／网页／JSON／X／公众号 adapter 是否够用，是否需要外部采集推送；凭据、服务供应商和暂停状态如何处理。
- 参与方式：用于正文编辑、只贡献热度信号，还是隔离保存；`tier`、`first_party` 和信号组各自表达不同含义。
- 内容使用：能抓全文与允许站内／RSS 展示全文是两件事，普通来源沿用默认摘要加原文链接；公众号本站全文的已批准例外见[信源指南](sources.md#分级参与方式与全文)。

配置和试抓操作以[信源指南](sources.md)为准。来源配置、SocialData 和 Wechat2RSS 的实施状态见[迁移清单](migration.md)，不以早期静态对比替代运行证据。生产切站与历史启动批已有记录；全历史余量和付费渠道授权仍按迁移清单及[回填运维](operations/backfill.md)确认，不由本开发地图扩大。

## 算法融合：逐个判断点比较

两边都经历采集、预筛、评分、富化和展示，但相同阶段名不代表相同决策函数。尤其不能把 Radar 的配额入选等同于 AIHOT 的绝对门槛，也不能把 Radar 的排名显示分当作 AIHOT 的平均评分。

后续每次算法改动应先指出它改变哪个判断点，再使用对应输入与标签验证：

| 判断点 | 可以接续的旧资产 | 在 AIHOT 基础上需要重新明确的部分 |
|---|---|---|
| 是否属于应收录的新闻 | O1 的材料与人工判断 | 三态预筛、缺失材料处理以及非新闻内容边界 |
| 是否入选、分数如何解释 | O2／O4 的可见分数、入选观察与人工复核 | 显示分、原始分、门槛、名额与来源限额分别起什么作用 |
| 分类、标题、摘要、推荐理由 | O3 的逐条材料、分类标注与错例 | structure 与写作阶段的职责、输入是否真的收到正文和引用 |
| 是否同一事件、事件如何变热 | 旧关联条目可作候选材料 | 旧体系未覆盖的事件身份和热度，需要单独定义验证对象，不能用分类指标代替 |

旧实验中的参照输出、人工标注、模型意见和当前运行材料应保持可区分；`pending` 不能当人工金标准。把旧案例拿来比较时，应保留原版本与原结论，另记录本仓实际收到的材料及新结果。改变对象或输入后取得的提升，只能在新比较口径下解释。

本仓已有[精选校准](selection.md)入口。它验证预筛和精选评分，不能自动证明分类、事件归组、排序或整个网站已完成对齐。本次仅整理开发依据，没有运行新评测，也没有选择新的生产模型或提示词。

## 后续开发从哪里开始

先把一个可观察的功能边界定清，再进入对应实现；以下是衔接次序，不是已经排期或获准执行的阶段计划。

1. **确认产品规则**：AI Radar 面向谁、展示哪些内容、如何解释精选与热门，以及哪些旧站体验需要保留。品牌文案、分类和条款按[定制指南](customize.md)确认。
2. **做最小来源接入**：从已映射的来源开始，在目标环境确认正文、时间、去重和来源角色正确，再扩大覆盖。静态来源数量不能替代这一步。
3. **比较算法行为**：用已有案例检查本仓默认链路，找到具体差异，再决定迁入旧规则、保留现有规则或形成新规则；不要先把所有旧提示词拼到一起。
4. **接入事件和阅读体验**：让精选、事件、热门和报告通过同一个公开读取层呈现，并核实最终读者看到的结果。
5. **接续迁移与发布**：先核迁移清单中已完成的切站与历史批次，再单独确定剩余历史内容、标注和实验资产的范围；本开发地图不新增生产操作授权。

### 新闻图片失败与恢复验收

`tests/media-recovery.test.ts` 使用本机图片服务验证 502 禁止浏览器／共享缓存、服务端 60 秒失败抑制、混合成功与失败的缓存复用及错误脱敏。`media.prepare` 完成独立图片后才抛出失败，沿既有队列最多重试一次、延迟 120 秒；不会自动回填全部历史。当前失败可查 pg-boss 的 job output，历史尝试按 worker 日志的既有保留期查询 `[media.prepare]`，用 `articleId`、`resourceId`（源 URL 的 SHA-256）和 `mode` 关联；API 日志同样包含资源标识、阶段和原因链，避免输出源 URL 的认证参数。

真实页面验收与常规 `scripts/smoke.ts` 分开：在浏览器打开新闻列表和详情，首屏及滚动后执行 `agent-browser eval --stdin < scripts/check-page-images.js`。它对当前视口已请求的实际 `currentSrc` 调用 `decode()`，返回解码尺寸、失败及回退状态，不输出签名 URL。正常图应有非零尺寸；失败的列表缩成文字、详情及大图提供原文链接、头像回退为首字。返回空图片集不能当通过，应选择确有新闻配图的条目。

对照至少包含正常图片和故意失败的图片；`tests/browser/media-recovery.html` 是无外部服务的组件 fixture，使用 `node --input-type=module -e 'import {createServer} from "vite"; const s=await createServer({configFile:false,server:{host:"127.0.0.1",port:55440},oxc:{jsx:{runtime:"automatic"}}}); await s.listen(); setTimeout(()=>s.close(),180000);'` 启动三分钟隔离服务，在 `/tests/browser/media-recovery.html` 可检查响应式候选失败、hydration 前已失败、按钮换资源恢复，以及正常视频缩略图。真实页面首次访问与同浏览器再次访问分别记录；浏览器首次不等于服务端冷缓存，冷缓存只在独占测试数据目录验证，不删除生产缓存。此检查证明图片传输与解码，不判新闻画面内容。部署后仍须从用户入口检查，不能以本地 fixture 代替真实出口。
