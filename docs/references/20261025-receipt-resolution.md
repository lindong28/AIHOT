## 决定与边界

明确审核拒绝包括安全错误分类与保存响应的 content_filter / refusal；明确请求拒绝仅接受 invalid_request 且 HTTP 400 / 422。能力协商的空 HTTP 状态不属于明确拒绝。拒绝不证明任何历史 provider attempt 未执行或未计费。保留真正未知的 timeout，不为清空列表重放。

业务结案必须匹配目标、当前版本及当前 attempt；时间下界使用被处置 attempt.started_at，缺失不结案，不能用 receipt.created_at。digest 结案核对当前 stories.version、对应持久化 story_digests 和已完成回执。既有 batch 的相同时间缺陷一并修正，保留后续失败保护。

后台使用全量聚合和分页，提供待处理、已处置历史；告警复用待处理语义，不再声称所有未知请求都重试过一次。错误保留安全类别、Gateway 固定错误码与输出截断原因，不保存自由上游错误或敏感请求。综述在既有生成次数和 token 预算内增加精简反馈，不截断接受不完整正文。

### 基础机制缺口与修复顺序

1. **诊断投影缺少拒绝细节。** Gateway `failure_details.py` 未匹配少数白名单代码的4xx会投影为invalid_request；AIHOT只保留类别/HTTP状态和少数code。已查ledger表结构、7条attempt、5条已有恢复检查点（均仅stop，无response），不足以恢复具体原因。应在Gateway到AIHOT统一保存有规范的安全错误码、参数名、provider request ID，以及正文字符/token估计、图片格式/大小/帧数；自由错误文本不能直接展示或记录。后台“上游未提供可安全保存的具体参数原因”超出证据，应改成“本系统未保留具体原因”。历史provider控制台/供应商日志未查，不宣称原因永久丢失。
2. **模型输入没有独立的图片规格约束。** `firstImagePart`直接复用网页thumb并内联base64；共享`resizeImage`为网页播放保留多帧原图。应给模型输入独立表示，按实际能力约束媒体和上下文，保留原图；不能全局改网页动图或一律截短正文。3个图片请求的能力需求均含image，同参数图片请求存在成功，不支持“GLM整条路由不支持图片”的结论。
3. **已拒绝请求缺少“修正后续跑”的完整入口。** `runUnderstand`的纯文本fallback只捕获`ProviderRejectedError`；Gateway路径抛`ReceiptUnknownError`/`ReceiptRecoveryStoppedError`，不会进入原分支。正确修法是仅对已确证可降级的图片/参数拒绝构建改变后的请求身份并关联旧问题；审核拒绝与真正未知保持各自保护，不把所有400当重试许可。
4. **按回执处理不足以表达文章进度。** 成功阶段已持久保存在receipts，但`runAnalysis`汇齐后才写analysis，任何未处理异常会让文章failed。应显示已完成/缺失阶段、依赖阻断，并在输入/模型/prompt身份兼容时复用已收到结果；当前规则要求两票评分，不能为了恢复改成一票。534528/534529应联合处置。业务结案、停止与历史核账分别保留，避免业务恢复后费用待核事项不可见。
